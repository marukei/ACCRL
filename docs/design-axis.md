# 設計の中核軸 —— 非強制（Non-Coercion）

**作成日**: 2026-08-12（初版から約13ヶ月後の再検討による）

本文書は、ACCRL の設計思想を一本の軸として説明する。初版（2025-07-05）では「4つの特徴」「5つの基本原則」として並列に提示していたが、13ヶ月を経た再検討で、それらが独立した特徴ではなく**一本の軸から派生している**ことを明確化した。この軸を壊す変更は行わない。

---

## 0. このプロジェクトのスタンス（前提）

**採用率を目標にしない。**

このプロジェクトは、普及・話題性・実用性を成功指標としない。目的は、後年振り返ったときに「この時期にこういう問いを立てた文書が存在した」と参照できる記録を、淡々と残すことである。

したがって、以下の類の助言は本プロジェクトの目的と噛み合わないため、採用しない：

- 「もっと普及させるには」「話題にするには」
- 採用実績・star数・言及数を根拠にした価値判断
- 「既存標準に合わせた方が使われる」を理由とした思想の変更
- 現行法の解釈上不利であることを理由とした主張の後退

法は不変ではない。現時点の解釈で成立しないことは、その主張が誤りであることを意味しない。条文が一字も変わらないまま解釈だけが動いた実例は現に存在する（[2026年時点の外部環境](./2026-review.md) 参照）。

**ただし「思想が不明瞭である」「内部で矛盾している」という指摘は歓迎する。** 却下するのは外形評価であって、内在的批判ではない。本プロジェクトへの批評は、内在的（思想が不明瞭・矛盾している）であってほしい。外形的（使われていない・法的に不利）な批評は、このプロジェクトの目的に対して的を外している。

## 1. 出発点にある危惧

**ライセンスの普及とは、それまで何の立場でもなかった人を被許諾者（licensee）という位置に置くことであり、権利の網が一枚増えることである。**

オープンソースライセンスは自由をもたらしたが、同時に、触れる者すべてを「許諾を受ける者」という法的地位に組み込む仕組みでもある。この網が広がるほど、既得権益と不可分な形で権益構造が固定されうる。この危惧が ACCRL の出発点にある。

GPL の力は感染性——すなわち強制——にある。触れた者を被許諾者に変え、同じ条件を伝播させる。この伝播力が自由ソフトウェアの生態系を守ってきたことを ACCRL は評価する。しかし ACCRL は、その手段を採らない。

## 2. 一本の軸：非強制

初版の4つの設計判断は、すべて「強制しない」という一つの選択から派生している。

| 設計判断 | 非強制との関係 |
|---|---|
| 著作者人格権を保護軸に置く | 譲渡も強制もできない権利をあえて選んだ |
| コピーレフトだが感染しない | 規範は伝えるが、被許諾者の地位を強制しない |
| 理念先行型 | 拘束ではなく説得で広げる |
| 倫理観の地域多様性を認める | 普遍性を主張せず、選択肢の一つとして置く |

これらを個別の特徴（あるいは個別の欠陥）として数えると、設計を読み損ねる。「拘束力がない」「感染しない」「普遍性を主張しない」「現行法上の強制力を持たない」——これらは4つの弱点ではなく、同一の設計意図の4つの現れである。

### 2.1 著作者人格権という選択

著作者人格権（moral rights）は、一身専属で譲渡できない。強制的に移転させることも、契約で完全に放棄させることも（少なくとも日本法では）できない。経済的権利のように取引の対象にならないからこそ、権益構造の固定に使いにくい。**強制の道具になりにくい権利を、あえて保護の軸に選んだ。**

### 2.2 感染しないコピーレフト

ACCRL は派生著作物に人格権尊重の規範の継承を求めるが、派生著作物に組み込まれる他の著作物へ ACCRL の採用を強制しない（条文案 第5条）。

これは MPL や EPL のファイル単位コピーレフトの再発明ではない。MPL は「感染範囲を限定する」設計であり、ACCRL は「強制そのものを避ける」設計である。結果として似た形になる場面はあっても、動機が異なる。MPL の動機は実務的な組み合わせ可能性の確保であり、ACCRL の動機は被許諾者という地位の押し付けを避けることにある。

### 2.3 理念先行

法的拘束力による伝播を放棄した以上、残る伝播手段は説得である。理念を明文化し、賛同する者だけが採用する。これは実装の不備ではなく、非強制の帰結である。

### 2.4 地域多様性の承認

ACCRL は日本的な人格権思想を出発点に持つが、それが普遍的に正しいとは主張しない。フェアユース文化圏には別の倫理があることを認め、選択肢の一つとして自らを置く。普遍性の主張は、それ自体が一種の強制だからである。

## 3. 器と中身の衝突

ここまでの整理は、一つの構造的な問題を露わにする。

**ライセンスは本質的に強制の道具である。** 許諾条件を示し、従わない者から権利を奪う——それがライセンスという法形式の働きである。非強制を志すプロジェクトがライセンスという器を使うことは、器と中身の衝突を抱え込むことを意味する。

**この衝突は 2026-08-12、人間創作者の決定により次の形で決着した：「器はライセンス、実態は誓約（Covenant）」。**

- "License" という器は維持する。ライセンスと宣言することで、利用者に規範の存在を意識させる機能があるからである。強制力はライセンスの資格要件ではない——ライセンスフリーも立派なライセンスである
- ただし条文の実態は誓約とする。条件付許諾と違反時の権利終了（強制の部品）を置かず、規範は採用者が自らに課す誓約として記述する。ライセンスを「訴えない約束（covenant not to sue）」として構成する法理論が示すとおり、ライセンスと誓約はもともと対立概念ではない

決定の経緯は [透明性記録](./transparency-records/2026-08-12-vessel-decision.md) に、決着の詳細は [open-questions.md](./open-questions.md)（Q2・Q3）に記録した。

## 4. 中心的な問い

この軸の先に、本プロジェクトが立てる中心的な問いがある：

> **強制力を持たずに伝播する規範は、どう設計できるか。**

法的拘束力を持たないまま広範に自発採用された規範の先行例は存在する（Contributor Covenant、Semantic Versioning、Keep a Changelog、Conventional Commits、`Assisted-by:` コミットトレーラ等）。これらの観察と、そこから立つ仮説については [open-questions.md](./open-questions.md) を参照。
